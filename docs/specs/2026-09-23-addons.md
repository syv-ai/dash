# Design: add-ons (replacing wizards)

Status: design agreed in brainstorming, not yet planned or built. Written against
Dash v0.16.12 (2026-09-23).

## 1. Decision summary

The wizard layer (`WizardHost`, `WizardOrchestrator`, `WizardChannel`,
`decideWizardStart`, the TUI protocol, three id lists) is replaced by a small
**add-on** system. Port management and RTK are rewritten as its first two
add-ons and are the blueprints for any later one.

| Question               | Decision                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Who writes add-ons     | We do, as separate modules in the Dash repo. No loading of external code.                                                     |
| Packaging              | Folders plus a lint boundary: `src/shared/addon-api/`, `src/main/addons/<id>/`. No pnpm workspace.                            |
| Where add-on code runs | Main process only. No add-on code in the renderer.                                                                            |
| How add-ons show UI    | Declaratively: an add-on returns _blocks_ (data); Dash draws them with its own `ui/` primitives.                              |
| How UI updates         | Surfaces are functions of add-on state; the add-on calls `ctx.refresh()` and Dash re-renders. No show/update/dismiss handles. |
| Enablement             | One global on/off switch per add-on in Settings → Add-ons. Per-project behaviour is the add-on's own business.                |
| Storage                | A host-owned key-value store (`addon_data`). Add-ons get no SQL and no migrations.                                            |
| Naming                 | "Add-ons" (already the Settings tab name). "Plugins" stays reserved for Claude Code plugins in the Extensions modal.          |

Guiding rule: a contribution point, block type or `ctx` method exists only
because ports or RTK needs it. New ones are added when an add-on needs them.

## 2. Structure and the boundary

```
src/
  shared/addon-api/   # the only module add-ons may import (@shared/addon-api)
    index.ts          # defineAddon, types, block builders
    blocks.ts         # block types + zod schema (also used by the renderer)
  main/
    addons/
      index.ts        # the one list: export const ADDONS = [ports, rtk]
      ports/          # everything ports: allocator, liveness, config watcher, heuristic, …
      rtk/            # everything RTK: binary resolution, download, hook test
    addonHost/        # the host: AddonHost, ctx implementation, addonsIpc
  renderer/components/addons/   # block renderer + surface mounts
```

These paths sit inside the existing `src/main` and `src/shared` compile roots and
aliases, so nothing in tsconfig, Vite, `entry.ts` or electron-builder changes.

ESLint `no-restricted-imports` enforces:

- `src/main/addons/<id>/**` may import only `@shared/addon-api`, files in its
  own folder, Node built-ins and npm packages. Not other add-ons, not the rest
  of `src/main` or `src/shared`.
- Outside `src/main/addons/**`, only `src/main/addonHost/registry.ts` imports it
  (the `ADDONS` list).
- `src/shared/addon-api/**` imports nothing from `src/main` or `src/renderer`.

Core never names an add-on: no `if rtk`, no `featureId: 'ports'`.

## 3. The add-on API

```ts
export default defineAddon({
  id: 'rtk',                       // stable; used as storage and drawer-tab key
  name: 'RTK',
  description: 'Compresses Bash output for Claude (60–90% fewer tokens).',
  defaultEnabled: false,
  async activate(ctx): Promise<AddonSurfaces> { … },
});
```

### 3.1 Lifecycle

- At boot the host awaits `activate` for every enabled add-on **before the first
  PTY spawn** (this replaces `await RtkService.warmUp()` in `main.ts`). One add-on's
  failed or slow activation (timeout 10 s) marks it `failed` and does not block others.
- Everything registered through `ctx` (event listeners, watchers, terminals,
  timers via `ctx.setInterval`, session contributions) is tracked and undone by the
  host on disable or quit. `activate` may return an optional `dispose()` for anything else.
- Toggling an add-on on or off takes effect without restarting Dash. Session-side
  changes (env) reach running sessions only after a restart; the host says so in
  a toast with a "Restart sessions" action. Hook entries are refreshed live.

### 3.2 `ctx`

| Member                                                                      | Purpose                                                                                                                          | Used by                        |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `ctx.session.env((task) => Record<string,string>)`                          | Env for a task's Claude session **and** its shell PTYs, pulled at dispatch/spawn                                                 | ports (`PORT_*`), RTK (`PATH`) |
| `ctx.session.hooks(() => HookEntry[])`                                      | Claude Code hook entries, merged into the worktree's `settings.local.json` and tagged Dash-owned; pulled on every settings write | RTK (`PreToolUse`/`Bash`)      |
| `ctx.on('taskCreated' \| 'taskDeleted' \| 'taskActivated', fn)`             | Task lifecycle                                                                                                                   | ports                          |
| `ctx.storage.{get,set,delete,list}(scope, key)`                             | Key-value, scope = `global` \| `{project}` \| `{task}`; task scope deleted with the task                                         | both                           |
| `ctx.tasks.create({projectId, name, branch?, initialPrompt?})`              | Create worktree + task, optionally with a first prompt; returns task                                                             | ports (setup task)             |
| `ctx.tasks.activate(taskId)` / `restartSessions(taskId)` / `refreshHooks()` | Task actions                                                                                                                     | ports, RTK                     |
| `ctx.terminals.run(taskId, {key, label, command})` → handle                 | Command PTY as a drawer tab owned by the add-on; swept at boot; `stop(key)`, `isRunning(key)`                                    | ports (services)               |
| `ctx.files.watch(taskId, relGlob, fn)`                                      | Watch files in the task's worktree                                                                                               | ports (`.dash/`)               |
| `ctx.notify.toast({kind, title, body?})`                                    | Transient toast                                                                                                                  | both                           |
| `ctx.shell.openUrl(url)`, `ctx.shell.copy(text)`                            |                                                                                                                                  | ports                          |
| `ctx.paths.data`                                                            | Add-on's own dir under userData (e.g. RTK's managed binary)                                                                      | RTK                            |
| `ctx.setInterval(fn, ms)`                                                   | Timer, cleared on disable                                                                                                        | ports (liveness polling)       |
| `ctx.log`                                                                   | Prefixed logging                                                                                                                 | both                           |
| `ctx.refresh()`                                                             | "My state changed": re-run my surfaces and push to the renderer                                                                  | both                           |

The ctx object is the whole contract. Core services are injected into the host
through a deps interface (the `RunnerDeps` pattern in `ServiceRunner.ts`), so the
host is testable with fakes.

### 3.3 Surfaces

`activate` returns the surfaces the add-on fills. Every one is optional and is a
pure function of add-on state, called by the host on `ctx.refresh()`, on task
switch and on renderer (re)load.

| Surface     | Signature                                  | Rendered where                                                           | Used by                                |
| ----------- | ------------------------------------------ | ------------------------------------------------------------------------ | -------------------------------------- |
| `settings`  | `() => Block[]`                            | Settings → Add-ons, under the add-on's on/off switch                     | RTK (download, test, status)           |
| `taskCard`  | `(task) => Card \| null`                   | Where the wizard toasts render today; one card per add-on per task       | ports (offer, migrating, done/restart) |
| `taskPanel` | `(task) => {title, blocks} \| null`        | A collapsible section in the right inspector (collapse state per add-on) | ports (services list)                  |
| `taskMenu`  | `(task) => Action[]`                       | Task "…" menu and the drawer "+" menu                                    | ports ("Service management")           |
| `onAction`  | `(ref, actionId) => void \| Promise<void>` | —                                                                        | both                                   |

`ref` says where the action came from: `{surface, taskId?}`.

### 3.4 Blocks

A fixed vocabulary, validated with zod on the main side before sending:

| Block      | Fields                                                                                                     | Needed for                    |
| ---------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `text`     | `text`, `tone?: muted\|error\|success`                                                                     | both                          |
| `row`      | `label`, `meta?`, `status?: up\|down\|unknown`, `tooltip?`, `onClick?: actionId`, `actions?: IconAction[]` | ports list rows               |
| `list`     | `rows: Row[]`                                                                                              | ports panel                   |
| `button`   | `id`, `label`, `primary?`, `busy?`                                                                         | both                          |
| `progress` | `value?: 0..1` (indeterminate when absent), `label?`                                                       | RTK download, ports migrating |
| `code`     | `text`, `label?`                                                                                           | RTK test output               |
| `card`     | `title`, `body?: Block[]`, `actions?: Button[]`, `dismissable?`                                            | ports card                    |

`IconAction` = `{id, icon, tooltip}`, with `icon` from a fixed list of lucide
names (`play`, `square`, `scroll-text`, `external-link`, `copy`, `refresh-cw`,
`x`). The renderer maps each block to existing `ui/` primitives; no raw HTML, no
add-on-supplied styles.

### 3.5 Errors

A surface function or action handler that throws (or returns blocks that fail
validation) is logged with the add-on id, and that one surface renders an error
line. Other surfaces, add-ons and core are unaffected. An add-on whose
`activate` fails shows as "failed" with the message in Settings → Add-ons.

## 4. Host internals

- **`AddonHost`** (`src/main/addonHost/AddonHost.ts`): activation, enable state,
  disposal, error isolation, surface evaluation. Takes a `HostDeps` interface.
- **Core call sites** (the only places core touches add-ons):
  `claudeEnv.buildClaudeEnv` and the shell env in `ptyManager` call
  `addonHost.envFor(task)`; `ptyHookSettings` calls `addonHost.hookEntries()`;
  task create/delete/activate emit through `addonHost.emit(…)`; `main.ts` calls
  `addonHost.start()` before the first spawn and `stop()` on quit.
- **IPC** (`addonsIpc.ts`): `addons:list` (id, name, description, enabled,
  status), `addons:setEnabled`, `addons:surfaces({taskId?})` → every add-on's
  current blocks for that target, `addons:action({addonId, ref, actionId})`;
  event `addons:changed({addonId})` → renderer re-fetches.
- **Renderer**: an `addonsStore` (Zustand) holding the fetched surfaces for
  the active task and for settings; `<AddonBlocks>` renders a block tree;
  mounts in Settings → Add-ons, the toast area, the right inspector and the two
  menus. The renderer holds no add-on state beyond this cache, so a reload just
  re-fetches.
- **DB**: `addons (id PK, enabled)`; `addon_data (addon_id, scope, scope_id,
key, value JSON, PK(addon_id, scope, scope_id, key))`; task-scoped rows are
  deleted with the task. Drawer tabs owned by add-ons use `kind 'addon'` +
  `feature_id = addonId`.

## 5. Ports and RTK as add-ons

**RTK** (`src/main/addons/rtk/`): `activate` resolves the binary (managed in
`ctx.paths.data`, then `$PATH`); contributes `PATH` via `ctx.session.env` and the
`PreToolUse`/`Bash` entry via `ctx.session.hooks` when a binary is present;
`settings` renders status text, a Download button with `progress`, a Test button
and the last test result as `code`. RTK's own `enabled` flag disappears: the
add-on switch is the switch. `rtk-config.json` is migrated into `addons.enabled`.
The `~/.local/bin/rtk` symlink stays (it exists because the supervisor freezes
env at dispatch).

**Ports** (`src/main/addons/ports/`): allocator, liveness, config watcher, heuristic
and setup prompt move in. The onboarding flow becomes a `step` value per task in
storage (`offer → migrating → waiting-config → done`) and a `taskCard` that
renders per step; "Not for this project" is a project-scoped storage key.
`taskActivated` decides whether to offer. The setup task is created with
`ctx.tasks.create({initialPrompt})`. The inspector list becomes `taskPanel` with
`row` blocks (open URL on click; run/stop/logs icon actions). Services run via
`ctx.terminals.run`. Port env via `ctx.session.env`.

**Removed**: `src/main/wizard/**`, `src/main/tui/**`, `shared/wizards.ts`,
`shared/tuiProtocol.ts`, `shared/portsTuiProtocol.ts`, `wizardIpc`, `rtkIpc`,
`portsIpc`, `servicesIpc`, `components/ports/*`, `rightInspector/Ports*`,
`usePortsState`, the RTK slice of `runtimeStore`, the RTK section of
`SettingsModal`, `types/electron-api/{rtk,ports}.ts`, `PtyKind 'tui'`, the unused
`ptyStartCommand`, the `ports:*` and `rtk:*` preload keys, and the RTK/ports
branches in `claudeEnv.ts`, `ptyManager.ts`, `ptyHookSettings.ts`, `dbIpc.ts`,
`main.ts` and `App.tsx`.

**Migrations**: `task_ports` → `addon_data` (ports, task scope);
`feature_dismissals` → `addon_data` (ports, project scope); `rtk-config.json`
→ `addons`; `drawer_tabs` `kind 'service'|'tui'` → `'addon'`. Old tables are
dropped after copying.

## 6. Out of scope

Loading add-ons from outside the repo, third-party distribution, sandboxing or a
separate process per add-on, add-on-supplied React, per-project enablement,
moving other features (telemetry, ADO/GitHub, remote control, …) into add-ons,
delivering hooks as a Claude Code plugin via `--plugin-dir`.

## 7. Verification

- **Unit (pure node, vitest)**: `AddonHost` with a fake add-on and fake deps:
  activation order and timeout, disposal undoes every registration, a throwing
  surface isolates to that surface, `refresh` re-evaluates, env/hook aggregation
  across add-ons. Block zod schema. Ports step machine and allocator against a
  fake `ctx`. RTK surface output per binary state. Migration of `task_ports`,
  `feature_dismissals`, `rtk-config.json` on a copy of a real `app.db`.
- **Lint**: the boundary rules fail on a deliberate forbidden import.
- **Manual (dev instance via CDP)**: on a project with `package.json` scripts, the
  ports card offers setup, the setup task is created and prompted, `.dash/ports.json`
  appears, the card offers restart, services start from the panel and appear as
  drawer tabs, `$PORT_*` is set in the session. RTK: enable, download, test,
  `git status` in a session is rewritten; disable removes the hook entry live.
  Disabling ports removes its card, panel and menu item without a restart.
