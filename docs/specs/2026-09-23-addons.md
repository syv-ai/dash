# Design: add-ons (replacing wizards)

Status: implemented on branch `addons-design` (v0.17.0). Plan:
`docs/specs/2026-09-23-addons-plan.md`. Written against Dash v0.16.12 (2026-09-23).

## 1. Decision summary

The wizard layer (`WizardHost`, `WizardOrchestrator`, `WizardChannel`,
`decideWizardStart`, the TUI protocol, three id lists) is replaced by a small
**add-on** system. Port management and RTK are rewritten as its first two
add-ons and are the blueprints for any later one.

| Question               | Decision                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Who writes add-ons     | We do, as separate modules in the Dash repo. No loading of external code.                                                     |
| Packaging              | Folders plus a lint boundary: `src/shared/addon-api/`, `src/main/addons/<id>/`. No pnpm workspace.                            |
| Where add-on code runs | Main process only. No add-on code in the renderer.                                                                            |
| How add-ons show UI    | Declaratively: an add-on returns _blocks_ (data); Dash draws them with its own `ui/` primitives.                              |
| How UI updates         | Surfaces are functions of add-on state; the add-on calls `ctx.refresh()` and Dash re-renders. No show/update/dismiss handles. |
| Where UI appears       | Two optional surfaces: a **settings** section and a collapsible **drawer**. No toasts-as-UI, menus or cards.                  |
| Drawer placement       | Per add-on user preference, Left or Right sidebar, set in Settings → Add-ons (default declared by the add-on).                |
| Enablement             | One global on/off switch per add-on in Settings → Add-ons.                                                                    |
| Storage                | A host-owned key-value store (`addon_data`). Add-ons get no SQL and no migrations.                                            |
| Naming                 | "Add-ons" (already the Settings tab name). "Plugins" stays reserved for Claude Code plugins in the Extensions modal.          |

Guiding rule: a surface, block type or `ctx` method exists only because ports or
RTK needs it. Every surface is optional; new ones are added when an add-on needs them.

## 2. Structure and the boundary

```
src/
  shared/addon-api/   # the only module add-ons may import (@shared/addon-api)
    index.ts          # defineAddon, types, block builders
    blocks.ts         # block types + zod schema (also used by the renderer)
  main/
    addons/
      index.ts        # the one list: export const ADDONS = [ports, rtk]
      ports/          # everything ports: allocator, liveness, heuristic, setup prompt, …
      rtk/            # everything RTK: binary resolution, download, hook test
    addonHost/        # the host: AddonHost, ctx implementation, store, file watch
  renderer/components/addons/   # block renderer, drawers, settings section
```

These paths sit inside the existing `src/main` and `src/shared` compile roots and
aliases, so nothing in tsconfig, Vite, `entry.ts` or electron-builder changes.

ESLint `no-restricted-imports` enforces:

- `src/main/addons/<id>/**` may import only `@shared/addon-api`, files in its
  own folder, Node built-ins and npm packages. Not other add-ons, not
  `electron`, not the rest of `src/main` or `src/shared`.
- Outside `src/main/addons/**`, only `src/main/addonHost/registry.ts` imports it
  (the `ADDONS` list).
- `src/shared/addon-api/**` imports nothing from `src/main` or `src/renderer`.

Core never names an add-on: no `if rtk`, no `featureId: 'ports'`.

## 3. The add-on API

```ts
export default defineAddon({
  id: 'rtk', // stable; used as storage and drawer-tab key
  name: 'RTK',
  description: 'Compresses Bash output for Claude (60–90% fewer tokens).',
  defaultEnabled: false,
  async activate(ctx): Promise<AddonSurfaces> { … },
});
```

### 3.1 Lifecycle

- At boot the host awaits `activate` for every enabled add-on **before the first
  PTY spawn** (this replaces `await RtkService.warmUp()` in `main.ts`). One add-on's
  failed or slow activation (timeout 10 s) marks it `failed` and does not block others.
- Everything registered through `ctx` (event listeners, session contributions,
  watchers, terminals, timers) is tracked and undone by the host on disable or
  quit. Surfaces may include an optional `dispose()` for anything else.
- Toggling an add-on on or off takes effect without restarting Dash. Hook
  entries are refreshed live. Env and `PATH` contributions reach running
  sessions only after a restart (the supervisor freezes the dispatch env); the
  host says so in a toast.

### 3.2 `ctx`

| Member                                                                             | Purpose                                                                                                                                                | Used by                                         |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| `ctx.session.env(({path, taskId}) => Record<string,string>)`                       | Synchronous env for a worktree's Claude session **and** shell PTYs, pulled at dispatch/spawn. Reserved keys (`PATH`, `HOME`, …) are ignored            | ports (`PORT_*`)                                |
| `ctx.session.path(() => string[])`                                                 | Directories prepended to `PATH` for the same PTYs                                                                                                      | RTK (managed bin dir)                           |
| `ctx.session.hooks(() => HookContribution[])`                                      | `{event: 'PreToolUse', matcher, command}` entries, merged into the worktree's `settings.local.json`, tagged Dash-owned; pulled on every settings write | RTK (`Bash`)                                    |
| `ctx.on('taskCreated' \| 'taskDeleted', fn)`                                       | Task lifecycle                                                                                                                                         | ports                                           |
| `ctx.storage.{get,set,delete}(scope, key)`, `list(scopeKind, key)`                 | Key-value; scope = `global` \| `{project}` \| `{task}`; task/project rows deleted with them                                                            | both                                            |
| `ctx.tasks.get(id)` / `list()`                                                     | `TaskInfo {id, projectId, name, path, archived}`                                                                                                       | ports (skip archived when checking taken ports) |
| `ctx.tasks.create({projectId, name, initialPrompt?})`                              | Create worktree + task, optionally with a first prompt                                                                                                 | ports (setup task)                              |
| `ctx.tasks.activate(id)` / `restartSessions(id)` / `refreshHooks()`                | Task actions                                                                                                                                           | ports, RTK                                      |
| `ctx.terminals.run(taskId, {key, label, command, cwd?, env?, onExit?, onClosed?})` | Command PTY as a drawer tab owned by the add-on; swept at boot; plus `stop`, `isRunning`, `focus(key, {reset?})`                                       | ports (services)                                |
| `ctx.files.watch(taskId, relDir, fn)`                                              | Watch a directory in the task's worktree, retrying until it exists                                                                                     | ports (`.dash/`)                                |
| `ctx.notify.toast({kind, title, body?})`                                           | Transient toast                                                                                                                                        | both                                            |
| `ctx.shell.openUrl(url)`, `ctx.shell.copy(text)`                                   |                                                                                                                                                        | ports                                           |
| `ctx.paths.data`                                                                   | Add-on's own dir under userData                                                                                                                        | RTK (managed binary)                            |
| `ctx.setInterval(fn, ms)`                                                          | Timer, cleared on disable                                                                                                                              | ports (liveness polling, setup timeout)         |
| `ctx.log`                                                                          | Prefixed logging                                                                                                                                       | both                                            |
| `ctx.refresh()`                                                                    | "My state changed": re-run my surfaces and push to the renderer                                                                                        | both                                            |

The ctx object is the whole contract. Core services are injected into the host
through a deps interface (the `RunnerDeps` pattern in `ServiceRunner.ts`), so the
host is testable with fakes.

### 3.3 Surfaces

`activate` returns the surfaces the add-on fills. **Every surface is optional**:
an add-on without `drawer` has no drawer, and one without `settings` shows only
its name, description and switch in Settings → Add-ons. Each is a pure function
of add-on state, called on `ctx.refresh()`, on task switch and on renderer (re)load.

| Surface    | Signature                                    | Rendered where                                                                                           | Used by |
| ---------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------- |
| `settings` | `() => Block[]`                              | Settings → Add-ons, under the add-on's on/off switch                                                     | RTK     |
| `drawer`   | `(task: TaskInfo \| null) => Drawer \| null` | A collapsible drawer in the left or right sidebar (per-add-on preference); `null` hides it for that task | ports   |
| `onAction` | `(ref, actionId) => void \| Promise<void>`   | —                                                                                                        | both    |

```ts
type Drawer = { title: string; summary?: string; actions?: IconAction[]; blocks: Block[] };
```

`defineAddon` may declare `drawerSide: 'left' | 'right'` (default `'right'`).
`ref` says where an action came from: `{surface: 'settings' | 'drawer', taskId?}`.

**Drawer placement.** The right sidebar stacks drawers where the ports drawer
sits today (bottom of the right inspector). The left sidebar stacks them at the
bottom of the expanded sidebar, above the update banner; they are hidden while
the left sidebar is collapsed to its rail. Collapse state and side are per add-on
renderer settings (`addonDrawerCollapsed`, `addonDrawerSide`); the side picker
appears in Settings → Add-ons only for add-ons that have a drawer.

### 3.4 Blocks

A fixed vocabulary, validated with zod on the main side before sending:

| Block      | Fields                                                                                                     | Needed for                |
| ---------- | ---------------------------------------------------------------------------------------------------------- | ------------------------- |
| `text`     | `text`, `tone?: muted\|error\|success`                                                                     | both                      |
| `row`      | `label`, `meta?`, `status?: up\|down\|unknown`, `tooltip?`, `onClick?: actionId`, `actions?: IconAction[]` | ports list rows           |
| `list`     | `rows: Row[]`                                                                                              | ports drawer              |
| `button`   | `id`, `label`, `primary?`, `busy?`                                                                         | both                      |
| `progress` | `value?: 0..1` (indeterminate when absent), `label?`                                                       | RTK download, ports setup |
| `code`     | `text`, `label?`                                                                                           | RTK test output           |

`IconAction` = `{id, icon, tooltip}`, with `icon` from a fixed list of lucide
names (`play`, `square`, `scroll-text`, `external-link`, `copy`, `refresh-cw`,
`x`). The renderer maps each block to existing `ui/` primitives; no raw HTML, no
add-on-supplied styles.

### 3.5 Errors

A surface function or action handler that throws (or returns blocks that fail
validation) is logged with the add-on id, and that one surface renders an error
line. Other surfaces, add-ons and core are unaffected. An add-on whose
`activate` fails shows as "failed" with the message in Settings → Add-ons.

## 4. Host internals

- **`AddonHost`** (`src/main/addonHost/AddonHost.ts`): activation, enable state,
  disposal, error isolation, surface evaluation. Takes a `HostDeps` interface.
- **Core call sites** (the only places core touches add-ons):
  `claudeEnv.buildClaudeEnv` and the shell env in `ptyManager` call
  `addonHost.envFor(…)` and `addonHost.pathDirs()`; `ptyHookSettings` calls
  `addonHost.hookEntries()`; task create/delete emit through `addonHost.emit(…)`;
  `main.ts` calls `addonHost.start()` before the first spawn and `stop()` on quit.
- **IPC** (`addonsIpc.ts`): `addons:list` (id, name, description, enabled,
  status, hasDrawer, drawerSide), `addons:setEnabled`, `addons:surfaces({taskId?})`
  → every add-on's current blocks for that target, `addons:action({addonId, ref, actionId})`,
  `addons:terminalClosed`; events `addons:changed({addonId})` → renderer re-fetches,
  plus the task/tab events `ctx` needs.
- **Renderer**: an `addonsStore` (Zustand) holding the fetched surfaces for the
  active task and for settings; `<AddonBlocks>` renders a block tree; mounts in
  Settings → Add-ons and in both sidebars. The renderer holds no add-on state
  beyond this cache and the two layout preferences, so a reload just re-fetches.
- **DB**: `addons (id PK, enabled)`; `addon_data (addon_id, scope, scope_id,
key, value JSON, PK(addon_id, scope, scope_id, key))`; task- and project-scoped
  rows are deleted with the task or project. Drawer tabs owned by add-ons keep
  `kind 'service'` with `feature_id = addonId`; `kind 'tui'` is removed.

## 5. Ports and RTK as add-ons

**RTK** (`src/main/addons/rtk/`): no drawer. `activate` resolves the binary
(managed in `ctx.paths.data`, then `$PATH`); contributes the managed bin dir via
`ctx.session.path` and the `PreToolUse`/`Bash` entry via `ctx.session.hooks`
when a binary is present; `settings` renders status text, an Install button with
`progress`, a Test button and the last test result as `code`. RTK's own
`enabled` flag disappears: the add-on switch is the switch. `rtk-config.json`
is migrated into `addons.enabled`. The `~/.local/bin/rtk` symlink stays (it
exists because the supervisor freezes env at dispatch).

**Ports** (`src/main/addons/ports/`): allocator, liveness, heuristic and setup
prompt move in. Setup is no longer offered unprompted: the ports **drawer** (right
by default) shows what fits the active task:

| Task state                                      | Drawer                                                                                                                                        |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| No `.dash/ports.json`, heuristic finds services | Text naming the detected signals and guessed services, and a **Start setup** button                                                           |
| No `.dash/ports.json`, nothing detected         | Short text on what port management does, and a **Start setup** button                                                                         |
| Setup started from this task                    | "Creating the port-setup task…" progress, then a line pointing to the new task                                                                |
| The port-setup task, waiting                    | "Waiting for the agent to write `.dash/ports.json`" progress, plus validation errors if the file is invalid; error text after 30 minutes      |
| The port-setup task, config landed              | "Allocated N ports" and a **Restart sessions** button (plus a one-off toast)                                                                  |
| Configured                                      | The ports list: rows with status, `:port`, open-URL on click, run/stop/logs actions; header summary "n/m up" and Run all / Stop all / Refresh |

"Start setup" creates the setup task with `ctx.tasks.create({initialPrompt})` and
activates it. The per-task setup step lives in task-scoped storage. There is no
auto-offer, snooze or per-project dismissal: collapsing the drawer is how a user
ignores it. Services run via `ctx.terminals.run`; port env via `ctx.session.env`.

**Removed**: `src/main/wizard/**`, `src/main/tui/**`, `shared/wizards.ts`,
`shared/tuiProtocol.ts`, `shared/portsTuiProtocol.ts`, `wizardIpc`, `rtkIpc`,
`portsIpc`, `servicesIpc`, `PortsConfigWatcher`, `components/ports/*`,
`rightInspector/Ports*`, `usePortsState`, the drawer "+" menu's Wizards group,
the RTK slice of `runtimeStore`, the RTK section of `SettingsModal`,
`types/electron-api/{rtk,ports}.ts`, `PtyKind 'tui'`, the unused
`ptyStartCommand`, the `ports:*`, `wizard*` and `rtk:*` preload keys, and the
RTK/ports branches in `claudeEnv.ts`, `ptyManager.ts`, `ptyHookSettings.ts`,
`dbIpc.ts`, `main.ts` and `App.tsx`.

**Migrations**: `task_ports` → `addon_data` (ports, task scope);
`feature_dismissals` is dropped (no dismissals any more); `rtk-config.json` →
`addons`; `drawer_tabs` rows of `kind 'tui'` deleted. Old tables are dropped
after copying.

## 6. Out of scope

Loading add-ons from outside the repo, third-party distribution, sandboxing or a
separate process per add-on, add-on-supplied React, per-project enablement,
dragging drawers between sidebars, menus or cards as surfaces, moving other
features (telemetry, ADO/GitHub, remote control, …) into add-ons, delivering
hooks as a Claude Code plugin via `--plugin-dir`.

## 7. Verification

- **Unit (pure node, vitest)**: `AddonHost` with a fake add-on and fake deps:
  activation and timeout, disposal undoes every registration, a throwing surface
  isolates to that surface, `refresh` re-evaluates, env/path/hook aggregation
  across add-ons, an add-on without a drawer contributes none. Block zod schema.
  Ports step logic, drawer output per state, and allocator against a fake `ctx`.
  RTK settings output per binary state. Migration of `task_ports` and
  `rtk-config.json` on a copy of a real `app.db`.
- **Lint**: the boundary rules fail on a deliberate forbidden import.
- **Manual (dev instance via CDP)**: on a project with `package.json` scripts, the
  ports drawer shows the detected services and Start setup; the setup task is
  created, activated and prompted; `.dash/ports.json` appears; the drawer offers
  Restart sessions; services start from the drawer and appear as drawer tabs;
  `$PORT_*` is set in the session. Moving the ports drawer to the left sidebar in
  Settings moves it. RTK: enable, install, test, `git status` in a session is
  rewritten; disable removes the hook entry live. Disabling ports removes its
  drawer without a restart.

## 8. As built

Differences from the design above, found while implementing:

- `ctx.shell.exec(command, cwd)` exists (ports' stop commands need a login
  shell with the host terminal's env stripped, which only core knows how to do).
- `ctx.files.watch` passes the changed file names to its callback and returns a
  disposer, so ports stops watching a deleted task's worktree right away.
- `TaskInfo` carries `useWorktree`; the ports drawer is only for worktree tasks.
- Add-on terminal tab ids are `service:<taskId>:<addonId>:<key>` (the renderer
  reads the task id from the second segment). Service tabs are swept at boot.
- The addon tables are plain SQL (`addonStore.ts`), not Drizzle schema, like
  `DrawerTabsService`.
- A hook contributed while no session is live lands on the next settings write
  (session start or restart); a live session gets it via `refreshHooks`.
- RTK's managed binary moved to `<userData>/addons/rtk/bin/`; the old
  `<userData>/bin/rtk` is moved on first activation and `~/.local/bin/rtk` is
  repointed (a dangling link is now repaired instead of failing).
- The renderer component is `AddonDock` (one per sidebar), not `AddonDrawerStack`.
